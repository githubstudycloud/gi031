# AI Metrics Patch Review Report

- Date: 2026-05-16
- Scope: split query/generation deployment and admin CRUD surface
- Conclusion: the patch introduces the intended split deployment shape and admin UI, but several new paths are not wired through end-to-end. Two issues are `P1` because they make supported-looking features misleading or unusable in common deployments.

## Findings

### P1. Admin metric definitions are exposed, but the report layer does not consume them

- Location: `app/api/admin.py:180-188`
- Related runtime paths: `fetch_summary()`, `preagg.refresh()`, `_derive_computed()`

**Problem**

The new admin surface allows creating metrics and editing fields such as `agg_method` and `computed_formula`, but report computation still relies on hard-coded metric definitions. Summary aggregation and pre-aggregation continue to use the static `ATOMIC_METRICS` list and the built-in `_derive_computed()` formulas.

**Impact**

- Newly created metric codes never appear in summary or pre-aggregation output.
- Changes to `agg_method` and `computed_formula` are silently ignored.
- `/admin/metrics` currently behaves like cosmetic metadata editing for anything beyond display labels.

**Recommendation**

- Either wire report computation to the persisted metric definitions, or
- temporarily restrict the admin API/UI so unsupported fields cannot be edited and new metrics cannot be created until the computation path is dynamic.

### P1. Admin page derives the generation URL from a hard-coded local port mapping

- Location: `admin/index.html:114-120`

**Problem**

The admin page assumes the generation tier is reachable by swapping between ports `8001` and `8002`. If the page is served from any other port arrangement, or through a reverse proxy on `80`/`443`, `GEN_URL` falls back to the current origin.

**Impact**

- `/api/admin/*` requests are sent to the query service instead of the generation service.
- `main_query` does not mount the admin router, so those requests return `404`.
- The `/admin/` page becomes unusable in deployments that do not exactly match the hard-coded local port pair.

**Recommendation**

- Derive the generation base URL from configuration rather than client-side port swapping.
- If the split must remain client-derived, pass the generation origin explicitly from the serving app or deployment environment.

### P2. Offline compose still runs the monolith on the supposed query tier

- Location: `deploy/docker-compose.offline.yml:27-30`

**Problem**

The offline `api` service is documented as the read-only query tier, but it still starts `app.main:app`, which includes ingest and admin routers.

**Impact**

- Port `8001` continues to expose write endpoints such as `/api/metrics/ingest` and `/api/admin/*`.
- The query/generation split is not actually enforced in the offline deployment.

**Recommendation**

- Start `app.main_query:app` for the query-tier service in offline compose so the read-only surface matches the documented deployment model.

### P2. Generation service health check still probes the old monolith endpoint

- Location: `deploy/docker-compose.offline.yml:35-38`

**Problem**

The compose file overrides the container command to run `app.main_generation` on port `8002`, but the reused image health check still probes `http://localhost:8001/api/healthz`. The generation app exposes `/healthz` instead.

**Impact**

- The generation container reports `unhealthy` even when the service itself is healthy.
- Health-based monitoring, restarts, or orchestration decisions can become noisy or incorrect.

**Recommendation**

- Override the service health check in `docker-compose.offline.yml` to probe the actual generation endpoint on port `8002`, for example `http://localhost:8002/healthz`.

## Summary

The main gap in this patch is consistency between the advertised surface and actual runtime behavior:

- The metric admin UI suggests dynamic metric computation, but the report layer remains static.
- The admin frontend assumes one fixed port topology and breaks outside that layout.
- The offline deployment claims a split topology, but the query tier still exposes write endpoints and the generation tier fails health checks by configuration.

These should be resolved before treating the split deployment and metric CRUD surface as production-ready.
